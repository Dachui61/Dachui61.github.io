# 2. 内容同步进本仓库，不在构建时去拉

- 状态：已接受
- 日期：2026-11-22
- 相关决定：3

## 上下文

本站的调研笔记和决策记录都产生在另一个工作仓库里（Vitals / Radar 所在
的仓库），那里才是它们被写出来的地方。

有两种做法：

- **A：构建时拉取**。CI 里 clone 另一个仓库，把内容取出来再构建。
- **B：内容同步进本站仓库**，构建时只读本仓库。

GitHub Pages 只能托管静态文件，构建发生在 GitHub 的 runner 上，
runner 上没有另一个仓库的凭据。A 方案要么把另一个仓库公开，要么给 CI
加一个只读 deploy key，要么改成从公开 API 拉——都引入了构建失败的新
原因，而且构建结果不再可复现。

## 决策

用 **B**，配一个同步脚本 `scripts/sync-content.mjs`：

1. 脚本从工作仓库读 `research/*.md` 和 `docs/adr/*.md`，抽出标题、日期、
   摘要，写成规范化的 frontmatter，落到 `content/work/`。
2. 工作仓库里的正文原样保留，不改一个字。
3. 中英文标题与摘要来自 `content/i18n/overrides.json`——手写，不自动翻译。
4. 同步结果**提交进本仓库**。CI 拿到的是一份确定的 JSON/Markdown，
   构建可复现，零外部依赖、零 API key。
5. 脚本是幂等的，可以随时重跑；`--check` 模式只报告差异不写文件。

## 后果

- **本仓库里的内容是副本。** 副本会过期。缓解办法是同步脚本随时可跑，
  而且工作仓库每次提交调研报告时顺手跑一次即可。
- **CI 不跑同步脚本。** 它需要的另一个仓库在 CI 里不存在，所以脚本在
  找不到源目录时会打印提示并跳过，不会失败。
- 内容与它产生的地方分离，这本身是个代价：改正文要在两个地方发生。
  这条只在「内容需要频繁修订」时才会疼，而调研报告是写完就基本不动的。

## 备选方案（被否掉的）

| 方案 | 否掉原因 |
|---|---|
| CI 里 clone 工作仓库 | 需要给 CI 凭据；构建依赖网络与另一个仓库的状态；构建不再可复现 |
| 从 GitHub API 拉工作仓库内容 | 工作仓库现在不是公开的；而且 API 有速率限制，是构建失败的新来源 |
| 把内容直接放在本仓库、不做同步 | 工作仓库才是内容产生的地方，复制粘贴会立刻产生两份互相漂移的真相 |
